## Introduction

Authentication and authorization are fundamental security mechanisms encountered in every digital platform. This document provides a comprehensive technical understanding of how these systems work, their evolution, and their modern implementations.

---

## Core Definitions

### Authentication
**Definition**: A mechanism to assign an identity to a subject and answer the question: **"Who are you?"**

- **Purpose**: Verify the identity of a user, device, or system
- **Context**: Can be a platform, operating system, application, or any digital environment
- **Process**: The method of determining and confirming identity

### Authorization
**Definition**: The process of determining **"What can you do?"** in a given context

- **Purpose**: Define capabilities, permissions, and access rights
- **Scope**: All actions a user can perform within a specific context
- **Technical Term**: Permissions, privileges, access control

```mermaid
graph TD
    A[User Access Request] --> B{Authentication}
    B -->|Success| C[Who are you?]
    B -->|Failure| D[Access Denied]
    C --> E{Authorization}
    E -->|Has Permission| F[What can you do?]
    E -->|No Permission| D
    F --> G[Grant Access to Resources]
```

### Era 4: Mid-20th Century (Computational Era - Mainframes)

#### **1961: MIT's Compatible Time-Sharing System (CTSS)**

**Breakthrough**: Introduction of passwords for multi-user systems

```mermaid

```

**The Critical Incident**:
- Passwords stored in **plain text**
- Someone printed the password file
- Vulnerability exposed
- Led to philosophy: **"Passwords should NEVER be stored in plain text"**

#### **Introduction of Hashing**

**Hashing Algorithm Properties**:

1. **Deterministic**: Same input always produces same output
2. **Fixed-Length Output**: Regardless of input size
3. **One-Way Function**: Computationally infeasible to reverse
4. **Avalanche Effect**: Small input change causes significant output change

**Mathematical Representation**:

$$
H: \{0,1\}^* \rightarrow \{0,1\}^n
$$

Where:
- $H$ = Hash function
- $\{0,1\}^*$ = Input of arbitrary length
- $\{0,1\}^n$ = Fixed-length output of $n$ bits

**Example**:
$$
\text{password} \xrightarrow{H} \text{5f4dcc3b5aa765d61d8327deb882cf99}
$$

**Core Security Principles Emerged**:
- **Confidentiality**: Information protected from unauthorized access
- **Integrity**: Data remains unaltered
- **Availability**: Systems accessible when needed

### Era 5: 1970s (Asymmetric Cryptography Revolution)

**Pioneers**: Whitfield Diffie and Martin Hellman

**Innovation**: **Diffie-Hellman Key Exchange**

```mermaid
sequenceDiagram
    participant A as Party A
    participant Public as Untrusted Medium
    participant B as Party B
    
    Note over A,B: Public Parameters: p (prime), g (generator)
    A->>A: Choose secret a
    B->>B: Choose secret b
    A->>Public: Send A = g^a mod p
    B->>Public: Send B = g^b mod p
    Public->>A: Receive B
    Public->>B: Receive A
    A->>A: Compute s = B^a mod p
    B->>B: Compute s = A^b mod p
    Note over A,B: Both parties now share secret s
```

**Mathematical Foundation**:

**Party A's Calculations**:
$$
A = g^a \mod p
$$

**Party B's Calculations**:
$$
B = g^b \mod p
$$

**Shared Secret Computation**:
$$
s = B^a \mod p = (g^b)^a \mod p = g^{ab} \mod p
$$

$$
s = A^b \mod p = (g^a)^b \mod p = g^{ab} \mod p
$$

**Result**: Both parties arrive at the same shared secret $s$ without transmitting it.

**Impact**:
- Enabled two parties to establish shared secrets over untrusted networks
- Foundation of modern authentication protocols
- Introduced **Public Key Infrastructure (PKI)**

#### **Post-Quantum Cryptography Explained**

**Problem**: Quantum computers can break current cryptographic algorithms

**Current Algorithms at Risk**:
- RSA
- Elliptic Curve Cryptography (ECC)
- Diffie-Hellman

**Why?**: Quantum computers can solve:
1. **Integer Factorization** (breaks RSA)
2. **Discrete Logarithm** (breaks DH and ECC)

Using algorithms like:
- **Shor's Algorithm**: Efficiently factors large numbers
- **Grover's Algorithm**: Speeds up brute-force searches

**Solution**: Post-quantum cryptographic algorithms resistant to quantum attacks

**Example Approaches**:
- Lattice-based cryptography
- Hash-based signatures
- Code-based cryptography
- Multivariate polynomial cryptography

## Three Fundamental Components

### 1. Sessions

#### **The Problem: HTTP Statelessness**

**HTTP Design Principle**: Stateless protocol

$$
\text{Request}_n \perp \text{Request}_{n-1}
$$

Each request is independent (⊥ denotes independence)

**Characteristics**:
- No memory of past exchanges
- Each request contains complete information
- Ideal for early web (static pages)

**Why Statelessness Became a Bottleneck**:

| **Use Case** | **Why Memory Needed** |
|--------------|----------------------|
| **E-commerce** | Remember shopping cart items |
| **User Sessions** | Keep users logged in across pages |
| **Personalization** | Maintain user preferences |
| **Workflows** | Track multi-step processes |

#### **Solution: Sessions**

**Session Workflow**:

```mermaid
sequenceDiagram
    participant C as Client (Browser)
    participant S as Server
    participant R as Redis/Database
    
    Note over C,S: Phase 1: User Login
    C->>S: POST /login (username, password)
    S->>S: Validate credentials
    S->>S: Generate Session ID
    S->>R: Store Session ID + User Data
    R-->>S: Confirmation
    S->>C: Set-Cookie: sessionId=abc123
    
    Note over C,S: Phase 2: Authenticated Request
    C->>S: GET /dashboard (Cookie: sessionId=abc123)
    S->>R: Fetch data for sessionId=abc123
    R-->>S: User data (id, role, cart items)
    S->>C: Dashboard content (personalized)
    
    Note over C,S: Phase 3: Session Expiry
    C->>S: GET /profile (Cookie: sessionId=abc123)
    S->>R: Check sessionId=abc123
    R-->>S: Session expired
    S->>C: Redirect to /login
```

**Session Components**:

1. **Session Creation**
   - Server generates unique Session ID
   - Stores user data alongside Session ID
   - Data stored in persistent store (Database/Redis)

2. **Session ID Transmission**
   - Sent to client as cookie
   - Automatically included in subsequent requests

3. **Session Validation**
   - Server retrieves session data using Session ID
   - Checks expiration
   - Validates user identity

4. **Session Expiration**
   - Time-based (e.g., 15 minutes)
   - Requires re-authentication after expiry

**Storage Evolution**:

```mermaid
graph LR
    A[File-Based Sessions] -->|Scalability Issues| B[Database Sessions]
    B -->|Performance Needs| C[Distributed In-Memory]
    
    A1[Session files on disk] -.-> A
    B1[MySQL/PostgreSQL] -.-> B
    C1[Redis/Memcached] -.-> C
    
    style C fill:#90EE90
```

**Comparison Table**:

| **Storage Type** | **Speed** | **Persistence** | **Scalability** | **Use Case** |
|------------------|-----------|-----------------|-----------------|--------------|
| **File-based** | Slow | High | Poor | Development only |
| **Database** | Moderate | High | Good | Small to medium apps |
| **Redis/Memcached** | Fast | Moderate* | Excellent | Large-scale production |

*Can be configured for persistence

### 2. JSON Web Tokens (JWT)

#### **The Problem with Sessions at Scale**

**Challenges by Mid-2000s**:

1. **Memory Overhead**
   $$
   \text{Memory Cost} = \text{Session Size} \times \text{Number of Users}
   $$
   - Millions of users = massive memory requirements

2. **Replication Latency**
   - Synchronizing session data across global servers
   - Consistency challenges
   - Network delays

3. **State Management Complexity**
   - Server coupling to session stores
   - Difficult horizontal scaling

#### **Solution: JSON Web Tokens (JWT)**

**Innovation**: Self-contained, stateless tokens

**JWT Structure**:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

**Three Parts** (separated by `.`):

```mermaid
graph TD
    A[JWT Token] --> B[Header]
    A --> C[Payload]
    A --> D[Signature]
    
    B --> B1["Algorithm & Type<br/>{alg: HS256, typ: JWT}"]
    C --> C1["Claims/Data<br/>{sub: user123, role: admin}"]
    D --> D1["Verification<br/>HMACSHA256(..., secret)"]
    
    style B fill:#e3f2fd
    style C fill:#fff9c4
    style D fill:#c8e6c9
```

#### **Part 1: Header**

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**Base64URL Encoded**: `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`

| **Field** | **Description** |
|-----------|-----------------|
| `alg` | Signing algorithm (HS256, RS256, etc.) |
| `typ` | Token type (always JWT) |

#### **Part 2: Payload (Claims)**

```json
{
  "sub": "user123",
  "name": "John Doe",
  "role": "admin",
  "iat": 1516239022,
  "exp": 1516242622
}
```

**Standard Claims**:

| **Claim** | **Full Name** | **Purpose** |
|-----------|---------------|-------------|
| `sub` | Subject | User ID/Identifier |
| `iat` | Issued At | Token creation timestamp |
| `exp` | Expiration | Token expiry timestamp |
| `iss` | Issuer | Who created the token |
| `aud` | Audience | Intended recipient |

**Custom Claims**: `name`, `role`, `email`, etc.

#### **Part 3: Signature**

**Purpose**: Verify token integrity and authenticity

**Algorithm (HMAC SHA-256)**:

$$
\text{signature} = \text{HMACSHA256}(\text{base64}(\text{header}) + "." + \text{base64}(\text{payload}), \text{secret})
$$

**Step-by-Step Signature Creation**:

1. **Encode header**:
   $$
   H_{\text{encoded}} = \text{Base64URL}(\text{header})
   $$

2. **Encode payload**:
   $$
   P_{\text{encoded}} = \text{Base64URL}(\text{payload})
   $$

3. **Concatenate**:
   $$
   \text{data} = H_{\text{encoded}} \, || \, "." \, || \, P_{\text{encoded}}
   $$

4. **Sign**:
   $$
   \text{signature} = \text{HMAC}(h, \text{data}, K_{\text{secret}})
   $$
   
   Where:
   - $h$ = Hash function (SHA-256)
   - $K_{\text{secret}}$ = Secret key

5. **Encode signature**:
   $$
   S_{\text{encoded}} = \text{Base64URL}(\text{signature})
   $$

6. **Final JWT**:
   $$
   \text{JWT} = H_{\text{encoded}} \, || \, "." \, || \, P_{\text{encoded}} \, || \, "." \, || \, S_{\text{encoded}}
   $$

**Verification Process**:

```mermaid
flowchart TD
    A[Receive JWT] --> B[Split into 3 parts]
    B --> C[Decode Header & Payload]
    C --> D[Recompute Signature]
    D --> E{Signatures Match?}
    E -->|Yes| F[Token Valid]
    E -->|No| G[Token Invalid/Tampered]
    F --> H[Extract User Data]
    G --> I[Reject Request]
    
    style F fill:#90EE90
    style G fill:#FFB6C6
```

#### **JWT Advantages**

| **Advantage** | **Description** | **Impact** |
|---------------|-----------------|------------|
| **Statelessness** | No server-side storage needed | Reduced infrastructure costs |
| **Scalability** | Works across distributed systems | Easy horizontal scaling |
| **Portability** | URL-safe, lightweight | Can be sent anywhere (headers, cookies, URLs) |
| **Microservices-Friendly** | Shared secret across services | Unified authentication |

#### **JWT Disadvantages**

| **Disadvantage** | **Description** | **Mitigation** |
|------------------|-----------------|----------------|
| **Token Theft** | If stolen, can be used until expiry | Short expiration times, secure transmission |
| **Cannot Invalidate** | No server-side revocation mechanism | Use hybrid approach with blacklists |
| **Token Size** | Larger than session IDs | Minimize payload data |
| **Secret Compromise** | If secret leaked, all tokens compromised | Regular secret rotation, use asymmetric keys |

#### **Hybrid Approach: Stateless + Stateful**

**Problem**: Need to revoke tokens immediately (account hack, malicious activity)

**Solution**: JWT + Token Blacklist

```mermaid
sequenceDiagram
    participant C as Client
    participant S as Server
    participant R as Redis (Blacklist)
    
    C->>S: Request with JWT
    S->>S: Verify JWT signature
    S->>R: Check if JWT in blacklist
    alt JWT in blacklist
        R-->>S: Token blacklisted
        S->>C: 401 Unauthorized
    else JWT not blacklisted
        R-->>S: Token valid
        S->>S: Extract user data from JWT
        S->>C: 200 OK (Response)
    end
    
    Note over S,R: When revoking access
    S->>R: Add JWT to blacklist
```

**Trade-off Analysis**:

| **Aspect** | **Pure JWT** | **Hybrid Approach** |
|------------|--------------|---------------------|
| **Storage lookup** | ❌ None | ✅ Blacklist check only |
| **Revocation** | ❌ Not possible | ✅ Immediate |
| **Performance** | ⚡ Fastest | ⚡ Near-instant (Redis) |
| **Complexity** | ✅ Simple | ⚠️ Moderate |

**Recommendation**: Use authentication providers (Auth0, Clerk) for production systems rather than implementing custom solutions.

### 3. Cookies

#### **What are Cookies?**

**Definition**: Small pieces of data stored in the browser by the server

**Key Property**: Server-side control with client-side storage

```mermaid
sequenceDiagram
    participant S as Server
    participant B as Browser
    
    Note over S,B: Setting a Cookie
    S->>B: HTTP Response<br/>Set-Cookie: sessionId=abc123; HttpOnly; Secure
    B->>B: Store cookie
    
    Note over S,B: Sending Cookie Automatically
    B->>S: HTTP Request<br/>Cookie: sessionId=abc123
    S->>S: Validate sessionId
    S->>B: HTTP Response (Authenticated)
```

#### **Cookie Attributes**

| **Attribute** | **Purpose** | **Example** |
|---------------|-------------|-------------|
| **Name=Value** | Cookie data | `sessionId=abc123` |
| **HttpOnly** | Prevents JavaScript access | ✅ Recommended for auth tokens |
| **Secure** | Only sent over HTTPS | ✅ Required in production |
| **SameSite** | CSRF protection | `Strict`, `Lax`, `None` |
| **Domain** | Which domain can access | `.example.com` |
| **Path** | Which paths can access | `/api/` |
| **Expires/Max-Age** | Cookie lifetime | `Max-Age=3600` (1 hour) |

**Setting a Cookie from Server**:

```http
HTTP/1.1 200 OK
Set-Cookie: authToken=xyz789; HttpOnly; Secure; SameSite=Strict; Max-Age=3600
```

**Automatic Cookie Transmission**:

```http
GET /api/profile HTTP/1.1
Host: example.com
Cookie: authToken=xyz789
```

#### **Cookie Security Features**

**1. Same-Origin Policy**: Cookies set by `server-a.com` cannot be read by `server-b.com`

**2. HttpOnly Flag**:
$$
\text{JavaScript Access} = 
\begin{cases}
\text{Allowed} & \text{if HttpOnly} = \text{false} \\
\text{Blocked} & \text{if HttpOnly} = \text{true}
\end{cases}
$$

**3. SameSite Protection**:

```mermaid
graph TD
    A[Request to site.com] --> B{SameSite Setting?}
    
    B -->|Strict| C[Only send if same-site navigation]
    B -->|Lax| D[Send on same-site + top-level GET]
    B -->|None| E[Always send requires Secure]
    
    C --> F[Strong CSRF Protection]
    D --> G[Balanced Protection]
    E --> H[No CSRF Protection]
    
    style F fill:#90EE90
    style G fill:#fff9c4
    style H fill:#FFB6C6
```

#### **Authentication Workflow with Cookies**

```mermaid
sequenceDiagram
    participant C as Client (Browser)
    participant S as Server
    
    Note over C,S: Step 1: Login
    C->>S: POST /login<br/>{username, password}
    S->>S: Validate credentials
    alt Authentication Success
        S->>S: Generate session ID/JWT
        S->>C: Set-Cookie: authToken=xyz<br/>HttpOnly; Secure
        Note over C: Browser stores cookie
    else Authentication Failed
        S->>C: 401 Unauthorized
    end
    
    Note over C,S: Step 2: Authenticated Requests
    C->>S: GET /dashboard<br/>Cookie: authToken=xyz
    S->>S: Validate token
    S->>C: Dashboard data
    
    C->>S: POST /api/data<br/>Cookie: authToken=xyz
    S->>S: Validate token
    S->>C: API response
```

**Advantages of Cookie-Based Auth**:
1. **Automatic**: Browser handles cookie transmission
2. **Secure**: HttpOnly prevents XSS attacks
3. **Server-Controlled**: Server can update/delete cookies
4. **CSRF Protection**: SameSite attribute

## Types of Authentication

### 1. Stateful Authentication

**Core Principle**: Server maintains session state

```mermaid
flowchart TD
    A[Client] -->|1. Login credentials| B[Server]
    B -->|2. Validate| C{Valid?}
    C -->|No| D[Reject]
    C -->|Yes| E[Generate Session ID]
    E --> F[Bundle user data]
    F --> G[(Redis/Database)]
    G -->|Store| H[Session ID + User Data]
    E -->|3. Send Session ID| I[Client stores in cookie]
    I -->|4. Subsequent requests| J[Send cookie with Session ID]
    J --> B
    B -->|5. Lookup| G
    G -->|6. Retrieve user data| B
    B -->|7. Response| A
    
    style C fill:#fff9c4
    style G fill:#e1f5fe
    style H fill:#c8e6c9
```

**Detailed Workflow**:

**Step 1: Authentication**
$$
\text{Client} \xrightarrow{\text{username, password}} \text{Server}
$$

**Step 2: Session Creation**
$$
\text{Session ID} = \text{CryptoRandom}()
$$
$$
\text{Redis}[\text{Session ID}] \leftarrow \{\text{userID}, \text{role}, \text{cart}, \ldots\}
$$

**Step 3: Cookie Distribution**
$$
\text{Server} \xrightarrow{\text{Set-Cookie: sessionId}} \text{Client}
$$

**Step 4: Validation Loop**
$$
\forall \text{ request } r: \quad \text{Server} \xleftarrow{\text{Cookie: sessionId}} \text{Client}
$$
$$
\text{userData} \leftarrow \text{Redis}[\text{sessionId}]
$$

**Storage Requirements**:

$$
\text{Total Memory} = N_{\text{users}} \times S_{\text{session}}
$$

Where:
- $N_{\text{users}}$ = Number of active users
- $S_{\text{session}}$ = Average session data size

**Pros and Cons**:

| **Advantages** | **Disadvantages** |
|----------------|-------------------|
| ✅ Immediate revocation | ❌ Server memory overhead |
| ✅ Server control | ❌ Doesn't scale easily across regions |
| ✅ Detailed tracking | ❌ Requires persistent storage |
| ✅ Easy to invalidate | ❌ Session synchronization complexity |

### 2. Stateless Authentication

**Core Principle**: Token contains all necessary information

```mermaid
flowchart TD
    A[Client] -->|1. Login credentials| B[Server]
    B -->|2. Validate| C{Valid?}
    C -->|No| D[Reject]
    C -->|Yes| E[Generate JWT]
    E --> F[Sign with secret key]
    F -->|3. Send JWT| G[Client stores JWT]
    G -->|4. Subsequent requests| H[Send JWT in header/cookie]
    H --> B
    B -->|5. Verify signature| I{Valid JWT?}
    I -->|No| J[401 Unauthorized]
    I -->|Yes| K[Extract user data from JWT]
    K -->|6. Process request| L[Response]
    L --> A
    
    style C fill:#fff9c4
    style E fill:#e1f5fe
    style I fill:#fff9c4
    style K fill:#c8e6c9
```

**Detailed Workflow**:

**Step 1: Authentication**
$$
\text{Client} \xrightarrow{\text{username, password}} \text{Server}
$$

**Step 2: JWT Generation**

Create payload:
$$
P = \{\text{sub: userId}, \text{role: admin}, \text{iat: timestamp}\}
$$

Sign token:
$$
\text{JWT} = \text{Base64}(H) \, || \, "." \, || \, \text{Base64}(P) \, || \, "." \, || \, \text{HMAC}(H||P, K_{\text{secret}})
$$

**Step 3: Token Distribution**
$$
\text{Server} \xrightarrow{\text{JWT}} \text{Client}
$$

**Step 4: Validation**

For each request with JWT:

$$
\text{Verify}: \quad \text{HMAC}(H||P, K_{\text{secret}}) \stackrel{?}{=} \text{Signature from JWT}
$$

If match:
$$
\text{Extract}: \quad \text{userID} \leftarrow P[\text{sub}]
$$

**Comparison: Stateful vs Stateless**:

| **Aspect** | **Stateful (Sessions)** | **Stateless (JWT)** |
|------------|------------------------|---------------------|
| **Storage** | Server-side (Redis/DB) | Client-side (token) |
| **Scalability** | Requires shared storage | Excellent (no coordination) |
| **Revocation** | Immediate | Difficult (needs blacklist) |
| **Security** | Server controls everything | Token theft risk |
| **Performance** | Storage lookup required | No storage lookup |
| **Cross-domain** | Limited (same domain) | Easy (anywhere) |
| **Token size** | Small (ID only) | Larger (contains data) |
| **State** | Stateful | Stateless |

## Core Definitions

### Authentication
**Definition**: A mechanism to assign an identity to a subject and answer the question: **"Who are you?"**

- **Purpose**: Verify the identity of a user, device, or system
- **Context**: Can be a platform, operating system, application, or any digital environment
- **Process**: The method of determining and confirming identity

### Authorization
**Definition**: The process of determining **"What can you do?"** in a given context

- **Purpose**: Define capabilities, permissions, and access rights
- **Scope**: All actions a user can perform within a specific context
- **Technical Term**: Permissions, privileges, access control

```mermaid
graph TD
    A[User Access Request] --> B{Authentication}
    B -->|Success| C[Who are you?]
    B -->|Failure| D[Access Denied]
    C --> E{Authorization}
    E -->|Has Permission| F[What can you do?]
    E -->|No Permission| D
    F --> G[Grant Access to Resources]
```

#### **Introduction of Hashing**

**Hashing Algorithm Properties**:

1. **Deterministic**: Same input always produces same output
2. **Fixed-Length Output**: Regardless of input size
3. **One-Way Function**: Computationally infeasible to reverse
4. **Avalanche Effect**: Small input change causes significant output change

**Mathematical Representation**:

$$
H: \{0,1\}^* \rightarrow \{0,1\}^n
$$

Where:
- $H$ = Hash function
- $\{0,1\}^*$ = Input of arbitrary length
- $\{0,1\}^n$ = Fixed-length output of $n$ bits

**Example**:
$$
\text{password} \xrightarrow{H} \text{5f4dcc3b5aa765d61d8327deb882cf99}
$$

**Core Security Principles Emerged**:
- **Confidentiality**: Information protected from unauthorized access
- **Integrity**: Data remains unaltered
- **Availability**: Systems accessible when needed

### Era 5: 1970s (Asymmetric Cryptography Revolution)

**Pioneers**: Whitfield Diffie and Martin Hellman

**Innovation**: **Diffie-Hellman Key Exchange**

```mermaid
sequenceDiagram
    participant A as Party A
    participant Public as Untrusted Medium
    participant B as Party B
    
    Note over A,B: Public Parameters: p (prime), g (generator)
    A->>A: Choose secret a
    B->>B: Choose secret b
    A->>Public: Send A = g^a mod p
    B->>Public: Send B = g^b mod p
    Public->>A: Receive B
    Public->>B: Receive A
    A->>A: Compute s = B^a mod p
    B->>B: Compute s = A^b mod p
    Note over A,B: Both parties now share secret s
```

**Mathematical Foundation**:

**Party A's Calculations**:
$$
A = g^a \mod p
$$

**Party B's Calculations**:
$$
B = g^b \mod p
$$

**Shared Secret Computation**:
$$
s = B^a \mod p = (g^b)^a \mod p = g^{ab} \mod p
$$

$$
s = A^b \mod p = (g^a)^b \mod p = g^{ab} \mod p
$$

**Result**: Both parties arrive at the same shared secret $s$ without transmitting it.

**Impact**:
- Enabled two parties to establish shared secrets over untrusted networks
- Foundation of modern authentication protocols
- Introduced **Public Key Infrastructure (PKI)**

#### **Post-Quantum Cryptography Explained**

**Problem**: Quantum computers can break current cryptographic algorithms

**Current Algorithms at Risk**:
- RSA
- Elliptic Curve Cryptography (ECC)
- Diffie-Hellman

**Why?**: Quantum computers can solve:
1. **Integer Factorization** (breaks RSA)
2. **Discrete Logarithm** (breaks DH and ECC)

Using algorithms like:
- **Shor's Algorithm**: Efficiently factors large numbers
- **Grover's Algorithm**: Speeds up brute-force searches

**Solution**: Post-quantum cryptographic algorithms resistant to quantum attacks

**Example Approaches**:
- Lattice-based cryptography
- Hash-based signatures
- Code-based cryptography
- Multivariate polynomial cryptography

## Three Fundamental Components

### 1. Sessions

#### **The Problem: HTTP Statelessness**

**HTTP Design Principle**: Stateless protocol

$$
\text{Request}_n \perp \text{Request}_{n-1}
$$

Each request is independent (⊥ denotes independence)

**Characteristics**:
- No memory of past exchanges
- Each request contains complete information
- Ideal for early web (static pages)

**Why Statelessness Became a Bottleneck**:

| **Use Case** | **Why Memory Needed** |
|--------------|----------------------|
| **E-commerce** | Remember shopping cart items |
| **User Sessions** | Keep users logged in across pages |
| **Personalization** | Maintain user preferences |
| **Workflows** | Track multi-step processes |

#### **Solution: Sessions**

**Session Workflow**:

```mermaid
sequenceDiagram
    participant C as Client (Browser)
    participant S as Server
    participant R as Redis/Database
    
    Note over C,S: Phase 1: User Login
    C->>S: POST /login (username, password)
    S->>S: Validate credentials
    S->>S: Generate Session ID
    S->>R: Store Session ID + User Data
    R-->>S: Confirmation
    S->>C: Set-Cookie: sessionId=abc123
    
    Note over C,S: Phase 2: Authenticated Request
    C->>S: GET /dashboard (Cookie: sessionId=abc123)
    S->>R: Fetch data for sessionId=abc123
    R-->>S: User data (id, role, cart items)
    S->>C: Dashboard content (personalized)
    
    Note over C,S: Phase 3: Session Expiry
    C->>S: GET /profile (Cookie: sessionId=abc123)
    S->>R: Check sessionId=abc123
    R-->>S: Session expired
    S->>C: Redirect to /login
```

**Session Components**:

1. **Session Creation**
   - Server generates unique Session ID
   - Stores user data alongside Session ID
   - Data stored in persistent store (Database/Redis)

2. **Session ID Transmission**
   - Sent to client as cookie
   - Automatically included in subsequent requests

3. **Session Validation**
   - Server retrieves session data using Session ID
   - Checks expiration
   - Validates user identity

4. **Session Expiration**
   - Time-based (e.g., 15 minutes)
   - Requires re-authentication after expiry

**Storage Evolution**:

```mermaid
graph LR

    B -->|Performance Needs| C[Distributed In-Memory]
```

| **File-based** | Slow | High | Poor | Development only |

### 2. JSON Web Tokens (JWT)

#### **The Problem with Sessions at Scale**

**Challenges by Mid-2000s**:

1. **Memory Overhead**
   $$
   \text{Memory Cost} = \text{Session Size} \times \text{Number of Users}
   $$
   - Millions of users = massive memory requirements

2. **Replication Latency**
   - Synchronizing session data across global servers
   - Consistency challenges
   - Network delays

3. **State Management Complexity**
   - Server coupling to session stores
   - Difficult horizontal scaling

#### **Solution: JSON Web Tokens (JWT)**

**Innovation**: Self-contained, stateless tokens

**JWT Structure**:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

**Three Parts** (separated by `.`):

```mermaid
graph TD
    A[JWT Token] --> B[Header]
    A --> C[Payload]
    A --> D[Signature]
    
    B --> B1["Algorithm & Type<br/>{alg: HS256, typ: JWT}"]
    C --> C1["Claims/Data<br/>{sub: user123, role: admin}"]
    D --> D1["Verification<br/>HMACSHA256(..., secret)"]
    
    style B fill:#e3f2fd
    style C fill:#fff9c4
    style D fill:#c8e6c9
```

#### **Part 1: Header**

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**Base64URL Encoded**: `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`

| **Field** | **Description** |
|-----------|-----------------|
| `alg` | Signing algorithm (HS256, RS256, etc.) |
| `typ` | Token type (always JWT) |

#### **Part 2: Payload (Claims)**

```json
{
  "sub": "user123",
  "name": "John Doe",
  "role": "admin",
  "iat": 1516239022,
  "exp": 1516242622
}
```

**Standard Claims**:

| **Claim** | **Full Name** | **Purpose** |
|-----------|---------------|-------------|
| `sub` | Subject | User ID/Identifier |
| `iat` | Issued At | Token creation timestamp |
| `exp` | Expiration | Token expiry timestamp |
| `iss` | Issuer | Who created the token |
| `aud` | Audience | Intended recipient |

**Custom Claims**: `name`, `role`, `email`, etc.

#### **Part 3: Signature**

**Purpose**: Verify token integrity and authenticity

**Algorithm (HMAC SHA-256)**:

$$
\text{signature} = \text{HMACSHA256}(\text{base64}(\text{header}) + "." + \text{base64}(\text{payload}), \text{secret})
$$

**Step-by-Step Signature Creation**:

1. **Encode header**:
   $$
   H_{\text{encoded}} = \text{Base64URL}(\text{header})
   $$

2. **Encode payload**:
   $$
   P_{\text{encoded}} = \text{Base64URL}(\text{payload})
   $$

3. **Concatenate**:
   $$
   \text{data} = H_{\text{encoded}} \, || \, "." \, || \, P_{\text{encoded}}
   $$

4. **Sign**:
   $$
   \text{signature} = \text{HMAC}(h, \text{data}, K_{\text{secret}})
   $$
   
   Where:
   - $h$ = Hash function (SHA-256)
   - $K_{\text{secret}}$ = Secret key

5. **Encode signature**:
   $$
   S_{\text{encoded}} = \text{Base64URL}(\text{signature})
   $$

6. **Final JWT**:
   $$
   \text{JWT} = H_{\text{encoded}} \, || \, "." \, || \, P_{\text{encoded}} \, || \, "." \, || \, S_{\text{encoded}}
   $$

**Verification Process**:

```mermaid
flowchart TD
    A[Receive JWT] --> B[Split into 3 parts]
    B --> C[Decode Header & Payload]
    C --> D[Recompute Signature]
    D --> E{Signatures Match?}
    E -->|Yes| F[Token Valid]
    E -->|No| G[Token Invalid/Tampered]
    F --> H[Extract User Data]
    G --> I[Reject Request]
    
    style F fill:#90EE90
    style G fill:#FFB6C6
```

#### **JWT Advantages**

| **Advantage** | **Description** | **Impact** |
|---------------|-----------------|------------|
| **Statelessness** | No server-side storage needed | Reduced infrastructure costs |
| **Scalability** | Works across distributed systems | Easy horizontal scaling |
| **Portability** | URL-safe, lightweight | Can be sent anywhere (headers, cookies, URLs) |
| **Microservices-Friendly** | Shared secret across services | Unified authentication |

#### **JWT Disadvantages**

| **Disadvantage** | **Description** | **Mitigation** |
|------------------|-----------------|----------------|
| **Token Theft** | If stolen, can be used until expiry | Short expiration times, secure transmission |
| **Cannot Invalidate** | No server-side revocation mechanism | Use hybrid approach with blacklists |
| **Token Size** | Larger than session IDs | Minimize payload data |
| **Secret Compromise** | If secret leaked, all tokens compromised | Regular secret rotation, use asymmetric keys |

#### **Hybrid Approach: Stateless + Stateful**

**Problem**: Need to revoke tokens immediately (account hack, malicious activity)

**Solution**: JWT + Token Blacklist

```mermaid
sequenceDiagram
    participant C as Client
    participant S as Server
    participant R as Redis (Blacklist)
    
    C->>S: Request with JWT
    S->>S: Verify JWT signature
    S->>R: Check if JWT in blacklist
    alt JWT in blacklist
        R-->>S: Token blacklisted
        S->>C: 401 Unauthorized
    else JWT not blacklisted
        R-->>S: Token valid
        S->>S: Extract user data from JWT
        S->>C: 200 OK (Response)
    end
    
    Note over S,R: When revoking access
    S->>R: Add JWT to blacklist
```

**Trade-off Analysis**:

| **Aspect** | **Pure JWT** | **Hybrid Approach** |
|------------|--------------|---------------------|
| **Storage lookup** | ❌ None | ✅ Blacklist check only |
| **Revocation** | ❌ Not possible | ✅ Immediate |
| **Performance** | ⚡ Fastest | ⚡ Near-instant (Redis) |
| **Complexity** | ✅ Simple | ⚠️ Moderate |

**Recommendation**: Use authentication providers (Auth0, Clerk) for production systems rather than implementing custom solutions.

## Types of Authentication

### 1. Stateful Authentication

**Core Principle**: Server maintains session state

```mermaid
flowchart TD
    A[Client] -->|1. Login credentials| B[Server]
    B -->|2. Validate| C{Valid?}
    C -->|No| D[Reject]
    C -->|Yes| E[Generate Session ID]
    E --> F[Bundle user data]
    F --> G[(Redis/Database)]
    G -->|Store| H[Session ID + User Data]
    E -->|3. Send Session ID| I[Client stores in cookie]
    I -->|4. Subsequent requests| J[Send cookie with Session ID]
    J --> B
    B -->|5. Lookup| G
    G -->|6. Retrieve user data| B
    B -->|7. Response| A
    
    style C fill:#fff9c4
    style G fill:#e1f5fe
    style H fill:#c8e6c9
```

**Detailed Workflow**:

**Step 1: Authentication**
$$
\text{Client} \xrightarrow{\text{username, password}} \text{Server}
$$

**Step 2: Session Creation**
$$
\text{Session ID} = \text{CryptoRandom}()
$$
$$
\text{Redis}[\text{Session ID}] \leftarrow \{\text{userID}, \text{role}, \text{cart}, \ldots\}
$$

**Step 3: Cookie Distribution**
$$
\text{Server} \xrightarrow{\text{Set-Cookie: sessionId}} \text{Client}
$$

**Step 4: Validation Loop**
$$
\forall \text{ request } r: \quad \text{Server} \xleftarrow{\text{Cookie: sessionId}} \text{Client}
$$
$$
\text{userData} \leftarrow \text{Redis}[\text{sessionId}]
$$

**Storage Requirements**:

$$
\text{Total Memory} = N_{\text{users}} \times S_{\text{session}}
$$

Where:
- $N_{\text{users}}$ = Number of active users
- $S_{\text{session}}$ = Average session data size

#### **Pros and Cons of Stateful Authentication**

| **Advantages** | **Disadvantages** |
|----------------|-------------------|
| ✅ **Centralized Control**: Complete control over all sessions | ❌ **Memory Overhead**: Server memory costs for all active sessions |
| ✅ **Real-time Information**: Live data about active sessions | ❌ **Limited Scalability**: Difficult with distributed systems |
| ✅ **Easy Revocation**: Can immediately revoke access/logout users | ❌ **Operational Complexity**: Higher complexity in multi-region deployments |
| ✅ **Session Tracking**: Detailed monitoring of user activity | ❌ **Latency Issues**: Synchronization delays across servers |
| ✅ **Secure by Default**: Server maintains truth | ❌ **Session Store Dependency**: Requires persistent storage (Redis/DB) |

**Ideal Use Cases**:
- Web applications with moderate traffic
- Applications requiring strict session management
- Systems needing immediate access revocation
- Most SaaS-based models

### 2. Stateless Authentication (JWT-Based)

**Core Principle**: Token contains all necessary information

```mermaid
flowchart TD
    A[Client] -->|1. Login credentials| B[Server]
    B -->|2. Validate| C{Valid?}
    C -->|No| D[Reject]
    C -->|Yes| E[Generate JWT]
    E --> F[Sign with secret key]
    F -->|3. Send JWT| G[Client stores JWT]
    G -->|4. Subsequent requests| H[Send JWT in Authorization header]
    H --> B
    B -->|5. Verify signature| I{Valid JWT?}
    I -->|No| J[401 Unauthorized]
    I -->|Yes| K[Extract user data from JWT]
    K -->|6. Process request| L[Response]
    L --> A
    
    style C fill:#fff9c4
    style E fill:#e1f5fe
    style I fill:#fff9c4
    style K fill:#c8e6c9
```

**Detailed Workflow**:

**Step 1: Authentication**
$$
\text{Client} \xrightarrow{\text{username, password}} \text{Server}
$$

**Step 2: JWT Generation**

Create payload:
$$
P = \{\text{sub: userId}, \text{role: admin}, \text{iat: timestamp}\}
$$

Sign token:
$$
\text{JWT} = \text{Base64}(H) \, || \, "." \, || \, \text{Base64}(P) \, || \, "." \, || \, \text{HMAC}(H||P, K_{\text{secret}})
$$

**Step 3: Token Distribution**
$$
\text{Server} \xrightarrow{\text{JWT}} \text{Client}
$$

Client stores JWT (typically in localStorage or cookie)

**Step 4: Authorization Header**

Client sends JWT in Authorization header:
```http
GET /api/resource HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

**Step 5: Validation**

For each request with JWT:

$$
\text{Verify}: \quad \text{HMAC}(H||P, K_{\text{secret}}) \stackrel{?}{=} \text{Signature from JWT}
$$

If match:
$$
\text{Extract}: \quad \text{userID} \leftarrow P[\text{sub}]
$$

#### **Pros and Cons of Stateless Authentication**

| **Advantages** | **Disadvantages** |
|----------------|-------------------|
| ✅ **Scalability**: Excellent for distributed architectures | ❌ **Token Revocation**: Complex and difficult |
| ✅ **No Session Store**: No Redis/database dependency | ❌ **Token Theft Risk**: Valid until expiry if stolen |
| ✅ **Microservices-Friendly**: Shared secret across services | ❌ **Larger Size**: JWT bigger than session ID |
| ✅ **Mobile-Friendly**: Works without cookies | ❌ **Secret Compromise**: All users affected if secret leaked |
| ✅ **Stateless**: No server memory overhead | ❌ **Cannot Track Active Sessions**: No real-time session info |

**Ideal Use Cases**:
- APIs and distributed systems
- Mobile applications
- Scalable systems with servers across multiple regions
- Microservices architectures

**Why Called "Stateless"**:

The key difference is what the server needs to verify:

**Stateful**:
$$
\text{Valid?} = \text{Check}(\text{Redis}[\text{sessionId}])
$$

**Stateless**:
$$
\text{Valid?} = \text{Verify}(\text{JWT}, K_{\text{secret}})
$$

In stateless authentication, all user information needed is **contained within the JWT itself**. The server only needs its secret key to verify authenticity - no external storage lookup required.

#### **Comparison: Stateful vs Stateless**

| **Aspect** | **Stateful (Sessions)** | **Stateless (JWT)** |
|------------|------------------------|---------------------|
| **Storage** | Server-side (Redis/DB) | Client-side (token) |
| **Scalability** | Requires shared storage | Excellent (no coordination) |
| **Revocation** | Immediate | Difficult (needs blacklist) |
| **Security** | Server controls everything | Token theft risk |
| **Performance** | Storage lookup required | No storage lookup |
| **Cross-domain** | Limited (same domain) | Easy (anywhere) |
| **Token size** | Small (ID only) | Larger (contains data) |
| **State** | Stateful | Stateless |
| **Memory Cost** | $O(n)$ where $n$ = active users | $O(1)$ constant |

### 4. OAuth 2.0 and OpenID Connect

#### **The Delegation Problem**

**Pre-OAuth Challenges**:

1. **Password Fatigue**
   - Too many accounts to manage
   - Users reuse weak passwords (123456, "password")
   - Single breach compromises multiple accounts

2. **Resource Sharing Need**
   - Websites need access to other platforms' resources
   - Example: Travel app scanning Gmail for flight tickets
   - Example: Social media importing contacts from Google

```mermaid
graph TD
    A[User Has Multiple Accounts] --> B[Problem 1: Too Many Passwords]
    A --> C[Problem 2: Resource Sharing]
    
    B --> D[Reuse Passwords]
    B --> E[Weak Passwords]
    D --> F[Security Risk]
    E --> F
    
    C --> G[Need: App A access to App B resources]
    G --> H[Bad Solution: Share passwords]
    H --> I[Disaster!]
    
    style F fill:#FFB6C6
    style I fill:#FF6B6B
```

#### **The Disastrous Initial Solution: Password Sharing**

**Example**: Travel app needs Gmail access to scan tickets

**What happened**:
- Users shared Gmail password with travel app
- Travel app used password to access Gmail

**Problems**:

| **Problem** | **Description** |
|-------------|-----------------|
| **Full Access** | App gets EVERYTHING, not just tickets |
| **Cannot Limit Permissions** | No way to restrict access scope |
| **Cannot Revoke** | Must change password everywhere |
| **Security Breach** | One app compromise = all accounts compromised |

$$
\text{Shared Password} \Rightarrow \text{Full Account Access} \Rightarrow \text{Security Disaster}
$$

#### **The Delegation Problem Defined**

**Delegation**: Providing access to one platform's resources to another platform, programmatically, without sharing passwords

$$
\text{Platform A} \xrightarrow{\text{needs access}} \text{Platform B Resources}
$$

**Without**: Sharing Platform B password ❌

**Requirements**:
- ✅ Specific permissions only
- ✅ Revocable access
- ✅ No password sharing
- ✅ User controls what's shared

## OAuth 2.0 and OpenID Connect

### OAuth 1.0 (2007): The Birth of Delegation

**Innovation**: Engineers from Google and Twitter developed a revolutionary idea

**Core Concept**: Share **tokens** instead of **passwords**

```mermaid
graph TD
    A[Password-based] --> B[Full Account Access]
    A --> C[Cannot Revoke]
    A --> D[Security Risk]
    
    E[Token-based] --> F[Specific Permissions]
    E --> G[Revocable]
    E --> H[Secure]
    
    style A fill:#FFB6C6
    style E fill:#90EE90
```

**Token vs Password**:

| **Aspect** | **Password** | **Token** |
|------------|-------------|-----------|
| **Access Scope** | Everything in account | Specific permissions only |
| **Example** | Full Google account access | Only read Google Contacts |
| **Revocation** | Must change password everywhere | Revoke single token |
| **Security** | High risk if shared | Limited risk, specific scope |

**Example**:

```mermaid
graph LR
    A[Google Password] -->|Gives access to| B[Gmail]
    A --> C[Google Photos]
    A --> D[Calendar]
    A --> E[Drive]
    A --> F[Contacts]
    A --> G[Everything!]
    
    H[Token] -->|Read-only access| F[Contacts]
    H -.->|No access| B
    H -.->|No access| C
    H -.->|No access| D
    
    style A fill:#FFB6C6
    style H fill:#90EE90
```

### OAuth 1.0 Components

**Four Key Players**:

| **Component** | **Definition** | **Example** |
|---------------|----------------|-------------|
| **Resource Owner** | User who owns the data | You |
| **Client** | App requesting access | Facebook |
| **Resource Server** | Server hosting the data | Google (Contacts) |
| **Authorization Server** | Server issuing tokens | Google Auth Server |

#### **OAuth 1.0 Flow**

```mermaid
sequenceDiagram
    participant U as Resource Owner<br/>(You)
    participant C as Client<br/>(Facebook)
    participant AS as Authorization Server<br/>(Google Auth)
    participant RS as Resource Server<br/>(Google Contacts)
    
    Note over U,C: Step 1: Initiate
    U->>C: Want to import contacts
    C->>AS: Redirect user for authorization
    
    Note over U,AS: Step 2: Authenticate & Grant
    AS->>U: Show login & permissions screen
    U->>AS: Login + Approve permissions
    
    Note over AS,C: Step 3: Token Issued
    AS->>C: Send access token
    
    Note over C,RS: Step 4: Access Resources
    C->>RS: Request contacts with token
    RS->>C: Return contacts data
```

**Mathematical Flow**:

**Step 1**: User initiates
$$
\text{User} \xrightarrow{\text{request}} \text{Client (Facebook)}
$$

**Step 2**: Redirect to authorization
$$
\text{Client} \xrightarrow{\text{redirect}} \text{Auth Server (Google)}
$$

**Step 3**: User authenticates and grants
$$
\text{User} \xrightarrow{\text{login + permissions}} \text{Auth Server}
$$

**Step 4**: Token issued
$$
\text{Auth Server} \xrightarrow{\text{token}} \text{Client}
$$

**Step 5**: Access resources
$$
\text{Client} \xrightarrow{\text{token}} \text{Resource Server} \xrightarrow{\text{data}} \text{Client}
$$

**Key Achievement**: Solved delegation problem without password sharing! 🎉

### OAuth 2.0 (2010+): Simplification and Enhancement

**OAuth 1.0 Limitations**:

| **Problem** | **Impact** |
|-------------|-----------|

| **Cryptographic Signatures** | Error-prone, hard to debug |
| **Limited Flexibility** | One-size-fits-all approach |

#### **OAuth 2.0 Improvements**

**1. Bearer Tokens**

Simplified token format:

$$
\text{OAuth 1.0}: \quad \text{Complex Cryptographic Signature}
$$

$$
\text{OAuth 2.0}: \quad \text{Simple Bearer Token}
$$

**Bearer Token Example**:
```http

```

- More vulnerable than OAuth 1.0
- But **much simpler** to implement
- Trade-off: simplicity > maximum security

#### **OAuth 2.0 Flow Types**

**1. Authorization Code Flow** (Most Common)

**Use Case**: Server-side web applications

```mermaid

    participant U as User
    participant C as Client App
    participant AS as Auth Server

    C->>AS: 2. Request authorization
    AS->>U: 3. Login & consent
    U->>AS: 4. Approve
    AS->>C: 5. Authorization code
    C->>AS: 6. Exchange code for token<br/>(with client_secret)
    AS->>C: 7. Access token + Refresh token
    C->>RS: 8. API call with access token
    RS->>C: 9. Protected resource
```

**Key Feature**: Two-step process
- Step 1: Get authorization code
- Step 2: Exchange code for access token (server-to-server, more secure)

**2. Implicit Flow** (Deprecated)

**Use Case**: Browser-based apps (Single Page Applications)

**Why Deprecated?**: Security vulnerabilities
- Tokens exposed in browser
- No refresh tokens
- XSS attack risks

**Modern Alternative**: Authorization Code Flow with PKCE

**3. Client Credentials Flow**

**Use Case**: Machine-to-Machine (M2M) communication

```mermaid
sequenceDiagram
    participant S1 as Server A
    participant AS as Auth Server
    participant S2 as Server B
    
    S1->>AS: 1. Request token<br/>(client_id + client_secret)
    AS->>AS: 2. Validate credentials
    AS->>S1: 3. Access token
    S1->>S2: 4. API call with token
    S2->>S1: 5. Response
```

**No User Involvement**: Pure server communication

$$
\text{Server A} \xrightarrow{\text{credentials}} \text{Auth Server} \xrightarrow{\text{token}} \text{Server A} \xrightarrow{\text{token}} \text{Server B}
$$

**4. Device Code Flow**

**Use Case**: Devices with limited input (Smart TVs, IoT devices)

```mermaid
sequenceDiagram

    D->>D: 3. Display: "Go to url.com<br/>Enter code: ABC-123"

    U->>AS: 4. Visit URL, enter code
    AS->>U: 5. Login & consent
    U->>AS: 6. Approve
    
    D->>AS: 7. Poll for token
```

**Why Needed?**: Smart TVs don't have keyboards for easy login

**Flow**:
1. TV shows code: "ABC-123"
2. User enters code on phone/computer
3. TV polls auth server for token
4. User approves on phone
5. TV receives token

#### **OAuth 2.0 Token Types**

| **Token Type** | **Purpose** | **Lifetime** | **Use** |
|---------------|-------------|--------------|---------|
| **Authorization Code** | One-time exchange | ~10 minutes | Exchange for access token |
| **Access Token** | Access protected resources | 15-60 minutes | API requests |
| **Refresh Token** | Get new access token | Days to months | Token renewal |

**Token Lifecycle**:

```mermaid
stateDiagram-v2

    AuthCode --> AccessToken: Exchange code
    AccessToken --> Expired: Time passes
    Expired --> AccessToken: Use refresh token
    AccessToken --> [*]: User logs out
    
    note right of AccessToken: Short-lived (15-60 min)
    note right of Expired: Use refresh token for new access token
```

**Refresh Token Flow**:

```mermaid

    participant C as Client

    Note over C: Access token expired

    AS->>AS: Validate refresh token
    AS->>C: New access token<br/>(optionally new refresh token)
```

### The Missing Piece: Authentication

**OAuth 2.0 Limitation**: Great for **authorization**, but not **authentication**

$$
\begin{aligned}
\text{Authentication} &= \text{"Who are you?"} \\
\text{Authorization} &= \text{"What can you do?"}
\end{aligned}
$$

**OAuth 2.0 Solved**:
- ✅ What resources can be accessed (authorization)
- ✅ Permission scoping

**OAuth 2.0 Didn't Solve**:
- ❌ User identity verification (authentication)
- ❌ User information (name, email, etc.)

### Role-Based Access Control (RBAC)

**Definition**: Authorization technique where permissions are assigned to **roles**, and users are assigned to roles

```mermaid
graph TD
    A[Users] --> B[Assigned to Roles]
    B --> C[Roles have Permissions]
    C --> D[Permissions for Resources]
    
    E[Alice] --> F[Admin Role]
    G[Bob] --> H[User Role]
    I[Carol] --> J[Moderator Role]
    
    F --> K[Read, Write, Delete]
    H --> L[Read, Write]
    J --> M[Read, Write]
    
    K --> N[All Resources + Dead Zone]
    L --> O[Notes Only]
    M --> P[Notes + Moderate]
    
    style F fill:#FF6B6B
    style H fill:#4ECDC4
    style J fill:#FFD93D
```

#### **RBAC Components**

**Three Key Elements**:

$$
\text{User} \xrightarrow{\text{assigned to}} \text{Role} \xrightarrow{\text{has}} \text{Permissions}
$$

1. **Users**: Individual accounts
2. **Roles**: Job functions or access levels
3. **Permissions**: Actions on resources

**Mathematical Representation**:

$$
\begin{aligned}
U &= \text{Set of Users} \\
R &= \text{Set of Roles} \\
P &= \text{Set of Permissions} \\
\text{Assign}: U &\rightarrow R \\
\text{Grant}: R &\rightarrow \mathcal{P}(P)
\end{aligned}
$$

Where $\mathcal{P}(P)$ is the power set of permissions (any subset of permissions)

#### **Example RBAC Setup**

**Roles and Permissions**:

| **Role** | **Permissions** | **Resources** |
|----------|----------------|---------------|
| **User** | Read, Write, Delete | Notes only |
| **Moderator** | Read, Write, Delete, Moderate | Notes + flagged content |
| **Admin** | Read, Write, Delete, Manage | All resources + Dead Zone |

**Role Assignment**:

```mermaid

    C[Bob<br/>user_id: 2] --> D[User]
    E[Carol<br/>user_id: 3] --> F[Moderator]
    
    B --> G[Permissions:<br/>read, write, delete,<br/>access_dead_zone]
    D --> H[Permissions:<br/>read, write, delete]
    F --> I[Permissions:<br/>read, write, delete,<br/>moderate]
    
    style B fill:#FF6B6B
    style D fill:#4ECDC4
    style F fill:#FFD93D
```

#### **RBAC Workflow**

```mermaid
sequenceDiagram
    participant U as User
    participant S as Server
    participant DB as Database
    
    Note over U,S: Step 1: User Registration/Login
    U->>S: Register/Login
    S->>DB: Create user<br/>Assign default role: "user"
    DB-->>S: User created with role
    S->>U: Success (session/JWT)
    
    Note over U,S: Step 2: Authenticated Request
    U->>S: GET /api/dead-zone<br/>(with auth token)
    
    Note over S: Step 3: Extract User Identity
    S->>S: Verify token<br/>Extract user_id
    
    Note over S,DB: Step 4: Check Role
    S->>DB: SELECT role FROM users<br/>WHERE user_id = ?
    DB-->>S: role = "user"
    
    Note over S: Step 5: Check Permissions
    S->>S: Does "user" role have<br/>"access_dead_zone" permission?
    
    alt Has Permission
        S->>U: 200 OK (Dead zone data)
    else No Permission
        S->>U: 403 Forbidden<br/>"Insufficient permissions"
    end
```

**Step-by-Step**:

**Step 1: Role Assignment** (Registration/Admin action)
$$
\text{Assign}(\text{user}_{\text{id}}) = \text{role}
$$

**Step 2: Request with Token**
$$
\text{User} \xrightarrow{\text{token}} \text{Server}
$$

**Step 3: Extract Identity**
$$
\text{user}_{\text{id}} = \text{Extract}(\text{token})
$$

**Step 4: Lookup Role**
$$
\text{role} = \text{Database}[\text{user}_{\text{id}}]
$$

**Step 5: Check Permission**
$$
\text{permitted?} = (\text{requested\_permission} \in \text{Permissions}(\text{role}))
$$

**Step 6: Response**
$$
\text{Response} = 
\begin{cases}
200 \text{ OK} & \text{if permitted} \\
403 \text{ Forbidden} & \text{if not permitted}
\end{cases}
$$

#### **Middleware Implementation Pattern**

**Typical Backend Flow**:

```mermaid

    A[Request] --> B[Auth Middleware]
    B --> C{Valid Token?}
    C -->|No| D[401 Unauthorized]
    C -->|Yes| E[Extract user_id]
    E --> F[Lookup role]
    F --> G[Attach to Request]
    G --> H[Business Logic]
    H --> I{Has Permission?}
    I -->|No| J[403 Forbidden]
    I -->|Yes| K[Process Request]
    K --> L[Response]

    style I fill:#fff9c4

    style J fill:#FFB6C6
```

**Pseudocode**:

```javascript
// Middleware 1: Authentication
function authMiddleware(req, res, next) {
  const token = req.headers.authorization;
  const userId = verifyToken(token);
  
  if (!userId) {
    return res.status(401).json({ error: "Unauthorized" });
  }
  
  req.userId = userId;
  next(); // Pass to next middleware
}

// Middleware 2: Authorization
function checkRole(requiredPermission) {
  return async function(req, res, next) {
    const role = await db.getUserRole(req.userId);
    const permissions = getRolePermissions(role);
    
    if (permissions.includes(requiredPermission)) {
      next(); // User has permission
    } else {
      res.status(403).json({ error: "Forbidden" });
    }
  };
}

// Route with authorization
app.get('/api/dead-zone', 
  authMiddleware,
  checkRole('access_dead_zone'),
  (req, res) => {
    // Business logic here
    res.json({ data: deadZoneNotes });
  }
);
```

## Security Best Practices

### 1. Error Messages in Authentication

**Problem**: Helpful error messages leak information to attackers

#### **Bad Practice: Specific Error Messages**

```mermaid
sequenceDiagram
    participant A as Attacker
    participant S as Server
    
    Note over A: Test if email exists
    A->>S: Login: hacker@test.com / password123
    S->>A: Error: "User not found"
    
    Note over A: Email doesn't exist, try another
    A->>S: Login: real.user@company.com / password123
    S->>A: Error: "Incorrect password"
    
    Note over A: Email EXISTS! Now brute-force password
    A->>S: Login: real.user@company.com / password1
    A->>S: Login: real.user@company.com / 123456
    A->>S: Login: real.user@company.com / qwerty
```

**Information Leakage**:

| **Error Message** | **Information Leaked** | **Attack Vector** |
|-------------------|------------------------|-------------------|
| "User not found" | Username/email doesn't exist | Enumerate valid users |
| "Incorrect password" | Username exists, password wrong | Target password brute-force |
| "Account locked" | Valid account, tried too many times | Confirmed valid target |

**Attack Flow**:

$$
\begin{aligned}
\text{"User not found"} &\Rightarrow \text{Try different email} \\
\text{"Incorrect password"} &\Rightarrow \text{Email valid, brute-force password} \\
\text{"Account locked"} &\Rightarrow \text{Valid account confirmed}
\end{aligned}
$$

#### **Good Practice: Generic Error Messages**

```mermaid
sequenceDiagram
    participant A as Attacker
    participant S as Server
    
    A->>S: Login: hacker@test.com / password123
    S->>A: Error: "Authentication failed"
    
    A->>S: Login: real.user@company.com / wrong_password
    S->>A: Error: "Authentication failed"
    
    A->>S: Login: locked.account@company.com / password
    S->>A: Error: "Authentication failed"
    
    Note over A: No information gained!
```

**Unified Response**:

$$
\forall \text{ authentication failures: } \text{Response} = \text{"Authentication failed"}
$$

**Best Practice Examples**:

✅ **Good Messages**:
- "Authentication failed"
- "Invalid credentials"
- "Login unsuccessful"

❌ **Bad Messages**:
- "User not found"
- "Incorrect password"
- "Account locked due to too many attempts"
- "Email doesn't exist"

**Implementation**:

```javascript
// ❌ BAD: Specific error messages
async function login(email, password) {
  const user = await db.findUser(email);
  
  if (!user) {
    return { error: "User not found" }; // LEAKS INFO!
  }
  
  if (!verifyPassword(password, user.passwordHash)) {
    return { error: "Incorrect password" }; // LEAKS INFO!
  }
  
  if (user.isLocked) {
    return { error: "Account locked" }; // LEAKS INFO!
  }
  
  return { token: generateToken(user) };
}

// ✅ GOOD: Generic error message
async function login(email, password) {
  const user = await db.findUser(email);
  
  if (!user || 
      !verifyPassword(password, user.passwordHash) || 
      user.isLocked) {
    return { error: "Authentication failed" }; // SAFE!
  }
  
  return { token: generateToken(user) };
}
```

**When Friendly Messages are OK**:

✅ **Safe contexts**:
- Form validation errors (before submission)
- Password strength requirements
- Input format errors (not authentication-related)

```javascript
// These are OK - not authentication-related
"Password must be at least 8 characters"
"Email format is invalid"
"This field is required"
```

### 2. Timing Attacks

**Definition**: Attack that exploits differences in response time to gain information

#### **The Vulnerability**

**Typical Authentication Flow**:

```mermaid
    J -->|Yes| L[Return Success]
    
    style D fill:#FFB6C6
    style G fill:#FFB6C6
    style K fill:#FFB6C6
    style L fill:#90EE90
```

**Response Times**:

$$
\begin{aligned}
t_{\text{user not found}} &< t_{\text{account locked}} < t_{\text{wrong password}} \\
50\text{ms} &< 150\text{ms} < 350\text{ms}
\end{aligned}
$$

**Why Different Times?**

| **Failure Point** | **Operations Required** | **Time** |
|-------------------|------------------------|----------|
| **User not found** | 1. Database lookup | ~50ms |
| **Account locked** | 1. Database lookup<br/>2. Check lock status | ~150ms |
| **Wrong password** | 1. Database lookup<br/>2. Check lock status<br/>3. Hash password<br/>4. Compare hashes | ~350ms |

**Password Hashing is Slow** (by design):

```javascript
// Hashing is intentionally slow (security feature)
const bcrypt = require('bcrypt');
const saltRounds = 12; // Higher = slower = more secure

// This takes ~200-300ms deliberately!
const hash = await bcrypt.hash(password, saltRounds);
```

**Why Hashing is Slow**:
$$
t_{\text{hash}} \propto 2^{\text{cost factor}}
$$

Higher cost = exponentially slower = harder to brute-force

#### **Timing Attack Exploitation**

**Attacker's Strategy**:

```mermaid
sequenceDiagram
    participant A as Attacker
    participant S as Server
    
    Note over A: Test username: test@fake.com
    A->>S: Login: test@fake.com / password
    Note over S: User not found (fast)
    S->>A: Error (50ms)
    Note over A: Fast response = username invalid
    
    Note over A: Test username: real@company.com
    A->>S: Login: real@company.com / password
    Note over S: Wrong password (slow - hashing)
    S->>A: Error (350ms)
    Note over A: Slow response = username VALID!
```

**Attack Algorithm**:

```python
def timing_attack(email_list, password):
    valid_emails = []
    
    for email in email_list:
        start = time.time()
        response = login(email, password)
        elapsed = time.time() - start
        
        # Slow response indicates username exists
        if elapsed > 200:  # milliseconds
            valid_emails.append(email)
            print(f"Found valid email: {email}")
    
    return valid_emails
```

**Measurement Over Multiple Requests**:

$$
t_{\text{avg}} = \frac{1}{n} \sum_{i=1}^{n} t_i
$$

Attacker makes multiple requests to reduce noise from network latency

#### **Defenses Against Timing Attacks**

**1. Constant-Time Operations**

Use cryptographically secure comparison functions:

```javascript
// ❌ BAD: Regular comparison (timing leak)
function comparePassword(provided, stored) {
  return provided === stored; // Stops at first difference
}

// ✅ GOOD: Constant-time comparison
const crypto = require('crypto');

function comparePassword(provided, stored) {
  // Always compares entire length
  return crypto.timingSafeEqual(
    Buffer.from(provided),
    Buffer.from(stored)
  );
}
```

**Regular Comparison Issue**:

```
provided: "password123"
stored:   "password456"
         ^
         Stops here! (fast)

provided: "xassword456"
stored:   "password456"
^
Stops immediately! (fastest)
```

$$
t_{\text{comparison}} \propto \text{number of matching characters}
$$

**Constant-Time Comparison**:

$$
t_{\text{comparison}} = \text{constant} \quad \forall \text{ inputs}
$$

Always checks all characters regardless of differences

**2. Simulated Delay**

Add artificial delay to equalize response times:

```javascript
async function login(email, password) {
  const startTime = Date.now();
  const MIN_RESPONSE_TIME = 300; // ms
  
  let success = false;
  
  // Actual authentication logic
  const user = await db.findUser(email);
  if (user && await verifyPassword(password, user.hash)) {
    success = true;
  }
  
  // Calculate remaining time to reach minimum
  const elapsed = Date.now() - startTime;
  const delay = Math.max(0, MIN_RESPONSE_TIME - elapsed);
  
  // Wait if response was too fast
  await sleep(delay);
  
  if (success) {
    return { token: generateToken(user) };
  } else {
    return { error: "Authentication failed" };
  }
}
```

**Effect**:

$$
t_{\text{response}} \geq t_{\text{min}} \quad \forall \text{ requests}
$$

```mermaid
graph TD
    A[Auth Request] --> B{Processing Time}
    B -->|Fast 50ms| C[Add 250ms delay]
    B -->|Moderate 150ms| D[Add 150ms delay]
    B -->|Slow 350ms| E[No delay needed]
    
    C --> F[Total: 300ms]
    D --> F
    E --> F
    
    style F fill:#90EE90
```

**Trade-off**: Slower authentication for everyone, but secure against timing attacks

**3. Hash Every Request**

Always perform expensive operations, even when they're not needed:

```javascript
async function login(email, password) {
  const user = await db.findUser(email);
  
  // ALWAYS hash the provided password
  const providedHash = await bcrypt.hash(password, saltRounds);
  
  if (!user) {
    // User doesn't exist, but we already hashed password
    // Time taken is similar to valid user path
    return { error: "Authentication failed" };
  }
  
  // Compare hashes
  const match = await bcrypt.compare(password, user.passwordHash);
  
  if (match && !user.isLocked) {
    return { token: generateToken(user) };
  }
  
  return { error: "Authentication failed" };
}
```

**Time Equalization**:

$$
\begin{aligned}
t_{\text{invalid user}} &\approx t_{\text{valid user}} \\
\text{(both include hashing)}
\end{aligned}
$$

#### **Comprehensive Defense Strategy**

```mermaid
graph TD
    A[Timing Attack Defense] --> B[Constant-Time Comparisons]
    A --> C[Simulated Delays]
    A --> D[Always Hash]
    A --> E[Generic Errors]
    
    B --> F[crypto.timingSafeEqual]
    C --> G[Minimum response time]
    D --> H[Hash even for invalid users]
    E --> I[Same message all failures]
    
    F --> J[Secure Authentication]
    G --> J
    H --> J
    I --> J
    
    style J fill:#90EE90
```

**Defense Checklist**:

- ✅ Use constant-time comparison functions
- ✅ Implement minimum response time
- ✅ Always perform expensive operations (hashing)
- ✅ Use generic error messages
- ✅ Rate limiting (prevent mass timing measurements)
- ✅ Monitor for suspicious patterns

**Additional Protection: Rate Limiting**

```javascript
// Limit login attempts to prevent timing measurement
const rateLimit = require('express-rate-limit');

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 5, // 5 attempts per window
  message: 'Too many login attempts, please try again later'
});

app.post('/login', loginLimiter, handleLogin);
```

**Rate Limiting Effect**:

$$
n_{\text{attempts}} \leq n_{\text{max}} \text{ per time window}
$$

Makes mass timing measurements impractical

### Security Best Practices Checklist

#### **Password Security**
- ✅ Hash passwords (bcrypt, Argon2, PBKDF2)
- ✅ Use unique salt per user
- ✅ Minimum 12+ rounds/iterations
- ✅ Never store plain text

#### **Session Security**
- ✅ HttpOnly cookies
- ✅ Secure flag (HTTPS only)
- ✅ SameSite attribute (CSRF protection)
- ✅ Short expiration times
- ✅ Regenerate session ID on login

#### **JWT Security**
- ✅ Short expiration (15-30 minutes)
- ✅ Strong secret key (256+ bits)
- ✅ HTTPS only transmission
- ✅ Minimal payload data
- ✅ Refresh token rotation

#### **General Security**
- ✅ Generic error messages
- ✅ Timing attack protection
- ✅ Rate limiting
- ✅ MFA for sensitive operations
- ✅ Regular security audits
